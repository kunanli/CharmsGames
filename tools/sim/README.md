# 平衡模擬腳本

```bash
python3 tools/sim/juice_sim.py      # 震動／漂移／擠壓的數學性質
python3 tools/sim/seeker_sim.py     # 迷宮結構、貓 AI、M4 狀態機、難度
python3 tools/sim/fishing_sim.py    # 物件放置、死內容、寶箱達成率
python3 tools/sim/catch_sim.py      # Combo 可達性、寶箱達成率、頓格
```

只需要 Python 3，沒有任何相依套件。全部通過會 exit 0，有失敗 exit 1。

---

## 這些腳本為什麼存在

開發環境裡**沒有 Godot binary**，沒辦法自動跑遊戲。但這三款的平衡完全靠數值堆出來 —— 寶箱門檻、Combo 倍率、生成間隔、物件配額。用眼睛看程式碼判斷不出「金寶箱到底拿不拿得到」。

所以做法是：**把 GDScript 的邏輯移植成 Python，跑幾十到幾百局，用統計回答設計問題。**

這不是形式上的測試，它實際抓到過四個會出貨的 bug：

| 抓到的問題 | 沒抓到會怎樣 |
|---|---|
| Fishing 有永遠鉤不到的物件，包含 500 分的 Charm | 玩家看得到卻撈不到，會以為是 bug |
| Fishing 金寶箱在數學上拿不到（盤面上限 3070 < 門檻 3500） | 金寶箱是死的，沒人拿得到，但沒人知道為什麼 |
| Catch 的 Combo 整個機制是死的（40 局有 35 局停在 ×1） | GDD 說 Combo 是「拉開分差的關鍵」，實際上完全沒作用 |
| 震動振幅用平方時，小碰撞只有 0.24px、四捨五入後是 0 | 「走到邊界震一下」這個功能等於沒做 |
| Seeker 石化重生可在中央蹲點刷 1550 分 | 比銅寶箱門檻還多，分數曲線整個壞掉 |

**改任何數值之前先跑一次，改完再跑一次，比較數字。** 這比實機試玩快得多，也是唯一能回答「金寶箱達成率變成幾 %」的方法。實機試玩要留給手感問題（會不會暈、震動夠不夠爽、頓格是打擊感還是延遲），那些是模擬答不出來的。

## 同步紀律（重要）

腳本裡的常數是 **GDScript 的副本，不是同一份**。Python 讀不到 `.gd`，所以這是刻意接受的重複。

**改了 `.gd` 的數值，就要改對應腳本頂部的常數。** 每支腳本開頭都有一段標了「與 xxx.gd 同步」的常數區，改動集中在那裡。

不同步的後果是腳本會安靜地驗證一組不存在的數值 —— 比沒有測試更糟。如果不確定有沒有漂掉，最快的檢查是把 `.gd` 與腳本的常數區並排看一遍，數字不多。

## 各腳本在驗什麼

**`juice_sim.py`** —— 純數學，最穩定，改 `shared/juice.gd` 或 `fx.gd` 時跑。
驗 trauma 會精準歸零（指數衰減會留下永久的 ±1px 抽動）、漂移幀率無關、位移不超過背景多畫的 24px、輸出恆為整數、震動在 144fps 不會變成高頻嗡嗲、擠壓有回彈。最後會印一張**震動可見度表**，決定觸發表的值要設多少 —— ARCADE 的可見門檻在 trauma ≈ 0.19，SUBTLE 在 ≈ 0.30。

**`seeker_sim.py`** —— 迷宮全連通、出生格都在通路上、**沒有安全點**（貪婪 AI 配靜態目標可能卡進 limit cycle，讓玩家站著不動就無敵）、M4 石化狀態機 11 項、難度基準、撞牆頻率。

**`fishing_sim.py`** —— 死內容檢查、水層可及面積（鉤子範圍是倒三角形，淺層只有中深層的一半，配額要照這個算）、寶箱達成率，並示範「關掉族群補充後金寶箱變 0%」。

**`catch_sim.py`** —— Combo 可達性、寶箱達成率、移動速度對平衡的影響、**顧 Combo 的打法是否真的勝過搶高分**（GDD 的設計意圖），以及頓格不會偷走比賽時間。

---

## 腳本裡的 AI 是玩家的近似，不是真人

每支腳本都內建一個機器人玩家（Seeker 會閃避、Catch 顧 Combo、Fishing 挑高 CP 值的撈）。它們是**理性但不完美**的近似，數字要當成「一個熟練玩家大概打得到這個區間」，不是精準預測。

拿來比較不同設定之間的**相對差異**是可靠的（速度 60 → 95 讓金寶箱從 13% 變 36%），拿單一絕對數字去對外承諾則不可靠。
